# ask_qinlin

> 产品经理的技术架构师——读得懂任意代码库，说得出PM更容易理解的话。

这是一个 [Claude Code](https://claude.ai/code) skill，灵感来自合作者研发好友qinlin。它的核心价值是**消除产研协作中的信息不对称**：帮 PM 在和研发沟通之前，先读懂代码说什么，避免"研发说不清楚，PM 听不明白"的反复拉锯。

---

## 解决什么问题

- 不知道一个需求大概多大工作量，跟研发对齐效率低
- 不确定某个字段/接口/功能现在有没有，需要反复找研发确认
- PRD 写完了不知道有没有技术问题，提给研发后才发现遗漏
- 需求变了不知道影响哪些地方，上线前心里没底
- 出了 bug 不知道是前端还是后端的问题，不知道找谁

## 安装方式

将 `SKILL.md` 文件放入 Claude Code 的 skills 目录：

```bash
# macOS / Linux
~/.claude/skills/ask_qinlin/SKILL.md

# Windows
%USERPROFILE%\.claude\skills\ask_qinlin\SKILL.md
```

重启 Claude Code 后即可使用。

## 使用方式

直接用自然语言描述你的问题，skill 会自动识别场景并路由到对应的分析框架。

**你不需要记任何命令。** 只要是和研发协作相关的技术问题，直接说就好。

启动后 skill 会显示路由地图，并请你提供代码仓库路径：

```
欢迎使用 ask_qinlin 👋

我可以帮你处理以下场景：

  A 立项评估  —  做不做、多少人力
  B 现状查询  —  有什么、缺什么、怎么解释
  C 架构咨询  —  怎么设计、合不合理
  D PRD 审查  —  需求文档有没有技术问题
  E 变更评估  —  改哪里、影响什么
  F Bug 归属  —  问题出在哪、谁来查
  G 验收支撑  —  怎么测、上线查什么
```

---

## 7 个场景路由

### A 立项评估
**适用于**：写立项材料、评估可行性、估工作量、判断要不要做某个功能

当你问"多大工作量"这类模糊问题时，skill 会先确认你是需要正式立项材料，还是只想快速摸个底——两种情况输出深度不同。

**输出内容**：改动涉及哪几层 + 工作量量级（小/中/大/超大）+ 前端工作量说明 + 风险清单 + 可行性结论（✅/⚠️/❌）

---

### B 现状查询
**适用于**：查某个字段/接口/功能现在有没有、怎么实现的、有什么限制

**输出内容**：先给一句话直接回答（有/没有）→ 定位具体实现位置 → 字段/数据缺口 → 权限边界 → 边界场景提示 → 可选生成接口文档

---

### C 架构咨询
**适用于**：评估设计方案合不合理、基座怎么设计、多业务赋能怎么做、技术选型

对平台型产品 PM 尤其有用：帮你评估基座能力边界，建议什么放基座、什么留给业务层。

**输出内容**：现有架构解读 + 方案合理性评估 + 多方案对比 + 推荐建议 + 设计反模式识别

---

### D PRD 审查
**适用于**：需求文档写完了，提给研发之前想先过一遍

提供 PRD 文档 + 代码仓库路径，skill 对照代码库逐条核查。

**输出格式**：
```
## PRD 审查报告
### ✅ 技术上没问题的部分
### ⚠️ 需要确认的点
### ❌ 技术上有问题的部分
### 📋 建议补充的验收标准（AC）
```

---

### E 变更评估
**适用于**：需求有改动，想知道影响哪些地方

**输出内容**：先给结论（改动量级：配置级/接口级/架构级）→ 直接影响模块 → 上游/下游追溯 → 联动风险 → 是否需要数据迁移

---

### F Bug 归属
**适用于**：出了问题，不知道是前端还是后端，不知道找谁

**输出格式**：
```
归属判断：前端/后端/数据层/约定问题（置信度：高/中/低）
排查建议：
- 前端方向：...
- 后端方向：...
```

---

### G 验收支撑
**适用于**：要验收了、准备上线、需要测试用例或上线 checklist

**输出内容**：正向 + 异常验收用例 + 回归范围 + 上线 CheckList（含配置/数据迁移/回滚方案）+ B2B 多租户特殊提示

## 设计原则

- **代码为准**：所有分析基于实际代码，不靠文档和记忆；发现文档与代码不一致时以代码为准
- **业务语言**：输出结论给 PM 看，不给研发看——不堆砌类名和技术术语
- **量级诚实**：工作量估算给范围不给精确数字，说明主要不确定因素
- **协作导向**：结论是 PM 与研发共同讨论的起点，不替代研发判断，不制造对立
- **仓库无关**：每次使用时提供仓库路径，支持任意技术栈，不依赖固定项目

---

## 适合谁用

- **产品经理**：尤其适合涉及多租户、权限管理、平台基座设计的场景
- **需要频繁与研发对齐的 PM**：减少反复拉会的沟通成本

## 常见问题

**Q：需要提前配置什么吗？**
A：不需要。每次使用时 skill 会请你提供代码仓库路径，支持任意本地路径。

**Q：支持什么技术栈？**
A：任意技术栈。skill 直接读代码，不依赖特定框架。Java/Python/Go/Node.js 均可。

**Q：分析结果准确吗？**
A：基于代码的分析比口口相传准确。但建议把结论作为和研发对齐的起点，而非最终答案——代码之外还有部署配置、外部依赖等不在仓库里的信息。

**Q：为什么叫 ask_qinlin？**
A：qinlin是作者研发团队里的好友，擅长把复杂技术问题讲得清楚明白。这个 skill 试图把那种能力固化下来，让每个 PM 都有一个随时可以问的qinlin。
